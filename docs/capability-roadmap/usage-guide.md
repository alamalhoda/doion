# راهنمای استفاده از کاتالوگ قابلیت

**نقش این فایل:** SSOT **فرآیند** — چطور از این درخت برای برنامه‌ریزی، مرور شریک، و پیاده‌سازی اصولی استفاده شود. جایگزین کارت قابلیت، `taxonomy.md`، یا skill Think/Build نیست.

**مخاطب:** مالک محصول، همکار توسعه، و Agent در Chat 1/2 مهارت `ai-feature-implementation`.

اگر فقط می‌خواهید به شریک نشان دهید چه چیزی در راه است: [`README.md`](README.md) + [`INDEX.md`](INDEX.md) + کارت موج جاری کافی است. این راهنما برای **اجرای درست** است.

## ۲. چرخهٔ حیات (بدون پرش)

```text
draft → clarified → ready → in-build → shipped
                ↘ blocked یا deferred
```

معنی دقیق وضعیت در [`taxonomy.md`](taxonomy.md) است. اینجا فقط **دروازهٔ حرکت**:

| از | به | شرط |
|----|----|------|
| `draft` | `clarified` | مرور تیم/شریک؛ فرض‌ها با README قفل‌شده هم‌خوان؛ هیچ ⚠️ مسدودکننده روی کارت |
| `clarified` | `ready` | حداقل یک برش با شرایط پذیرش قابل تست؛ `blocked_by` آن برش خالی یا برش‌های پیش‌نیاز `shipped` |
| `ready` | `in-build` | Chat 1 شروع شده؛ `impl_path` به `ai-documents/features/<kebab>/` پر است |
| `in-build` | `shipped` | رفتار در کد (و در صورت لمس API همان PR قرارداد)؛ فلگ و failover طبق کارت؛ YAML + INDEX هم‌خوان |
| هر وضعیت | `blocked` | پیش‌نیاز فنی، شریک، یا حقوقی ندارد — کار روی برش زنده ممنوع |
| هر وضعیت | `deferred` | عمداً عقب افتاده؛ دلیل در کارت |

قوانین سخت:

- قابلیت **بدون برش** از `draft` بالاتر نمی‌رود مگر صریحاً «فقط مرجع، بدون اجرا».
- `in-build` بدون لینک `impl_path` ممنوع است.
- یک برش در هر لحظه روی یک شاخهٔ `feature/*`؛ برش را با کارت دیگر قاطی نکنید.
- `blocked` را با حدس در Chat 2 دور نزنید.

## ۳. انتخاب کار بعدی

1. [`INDEX.md`](INDEX.md) را باز کنید، نه پوشه را تصادفی.
2. موج را از بالا بخوانید (`W0` قبل از `W1`). ترتیب داخل موج اگر در INDEX آمده، همان را رعایت کنید.
3. ستونی **برش بعدی** را بردارید که وضعیت قابلیت `ready` یا `clarified` با برش آماده باشد — نه `blocked`.
4. فایل برش را بخوانید: `blocked_by`، خارج از محدوده، User Story.
5. کارت والد را بخوانید: مجوز، ریل، ⚠️ باز.
6. اگر لایهٔ استعلام/KYC/SMS/صیاد/اعتبار/امضا/OCR چک است: [`vendor-landscape.md`](vendor-landscape.md) را هم بخوانید — انتخاب vendor را به Think موکول کنید؛ در دامنه قفل نکنید.

اگر دو برش هم‌زمان وسوسه‌انگیزند: اول آن که `blocked_by` دیگری است (مثلاً `CY-003-a` قبل از `CY-008-a`). موازی فقط وقتی INDEX یا کارت صریح گفته (مثل `CY-005-a` و `CY-006-a` پس از دروازه).

## ۴. چه زمانی پیاده‌سازی را شروع نکنید

متوقف شوید اگر یکی از این‌ها برقرار است:

- برش یا قابلیت `blocked` یا `draft` بدون مرور است.
- سؤال ⚠️ روی کارت **مسیر پذیرش** را عوض می‌کند (مثلاً «بیومتریک اجباری است یا استعلام کافی است؟»).
- پیش‌نیاز برش (`blocked_by`) هنوز `shipped` نیست.
- می‌خواهید «کل CY-001» را یک‌جا بسازید به‌جای یک حرف (`a`/`b`/…).
- می‌خواهید روی `develop`/`master` کد بزنید.
- UI را از Cursor به ریپوی Studio پوش کنید.
- vendor را قبل از Port در مدل دامنه hard-code کنید.
- خروجی OCR را به‌جای استعلام صیاد حقیقت وضعیت برگه بگیرید.

کار درست در این حالت: کارت/برش را `clarified` کنید، یا برش پیش‌نیاز را تمام کنید، یا سؤال را با شریک ببندید — نه شروع Build.

## ۵. جریان اجرا (از برش تا ادغام)

یک برش = یک هدف = یک شاخهٔ کوتاه‌عمر. جزئیات Git در skill `gitflow-workflow` است؛ اینجا فقط ترتیب اصولی.

### ۵.۱ قبل از کد — آماده‌سازی

1. نقطهٔ ۱ GitFlow: `develop` را آینه کنید، بعد `feature/<slice-id>-<short-name>` بسازید (مثال: `feature/cy-001-b-identity-inquiry-port`).
2. در کارت والد و برش: `status` برش را به مسیر `ready` برسانید اگر هنوز نیست.
3. پرامپت Chat 1 را از **بلوک User Story داخل فایل برش** بسازید، نه از حافظه. قالب پوسته: `start-prompt.md`.
4. در Additional Context حتماً باشد: مسیر کارت والد، خارج از محدودهٔ برش، ریل تسویه، و در صورت اتصال بیرونی ارجاع به `vendor-landscape.md`.

نمونهٔ حداقل پرامپت:

```text
@ai-feature-implementation
لطفاً این ویژگی را دقیقاً مطابق skill پیش ببر.
دو چت Think سپس Build. فعلاً وارد کدنویسی نشو.

[بلوک User Story را از فایل برش عیناً بچسبانید]

همچنین بخوان و رعایت کن:
- docs/capability-roadmap/usage-guide.md
- کارت والد و همین فایل برش
```

### ۵.۲ Chat 1 — THINK (بدون کد)

Skill را صریح صدا بزنید (`@ai-feature-implementation`). چرخهٔ کوچک یا باگ این مهارت نیست.

ترتیب اجباری:

1. شفاف‌سازی — فقط سؤال؛ جواب انسان.
2. `feature_spec.md` — WHAT قابل تست، نه HOW.
3. تأیید طراحی، بعد `implementation_plan.md`.

اگر برش KYC / SMS / صیاد / اعتبار / امضا / OCR چک است: قبل از Step 2 همان Chat، پرامپت تحقیق [`vendor-landscape.md`](vendor-landscape.md) را اجرا کنید و `vendor-score.md` را کنار spec بگذارید. Port داخلی را در spec قفل کنید؛ نام vendor فقط در طرح آداپتر.

خروجی را commit کنید، بعد Chat 2 را در چت تازه با spec + plan شروع کنید.

پوشهٔ پیشنهادی: `ai-documents/features/cy-NNN-x-kebab/`.

### ۵.۳ Chat 2 — BUILD

- یک قدم پلن در هر نوبت؛ تست از روی spec نه از روی کد.
- دامنه (`doion.identity`، `checks`، `matching`) به URL vendor وابسته نشود.
- فلگ خاموش = رفتار فعلی لایه ۱. قطع تأمین‌کننده = صف دستی / stub، نه `approved` خاموش.
- UI فقط از مسیر Google AI Studio.
- تغییر serializer/view/url در **همان PR** با به‌روزرسانی `MASTER_API_CONTRACT.md`.
- venv: `source backend/.venv/bin/activate` قبل از pytest.

### ۵.۴ قبل از PR و بعد از merge

- نقطهٔ ۲ GitFlow: merge با `origin/develop` (rebase فقط اگر صریح خواسته شود).
- PR به `develop`، نه merge محلی روی `develop`.
- در توضیح PR: برش (`CY-NNN-x`)، وضعیت تست، و `Docs updated` یا `Docs impact: none`.
- پس از merge: نقطهٔ ۳ (پاک‌سازی شاخه + prune).
- کارت و INDEX: `shipped` فقط وقتی رفتار در `develop` است. `impl_path` بماند برای ردگیری.
- اگر رفتار محصول جاری عوض شد: سند پایه / Core Brief در همان موج مستند، نه بعداً «یادمان باشد».

تگ SemVer روی `feature/*` نزنید. انتشار جدا است (`semver-release`).

## ۶. قوانین دامنه هنگام ساخت از روی کارت

این‌ها از فرض‌های README و کارت‌ها می‌آیند؛ در spec نقض‌شان یعنی برش اشتباه است.

- در `W1` معاملهٔ اجراشده فقط `partner_trade` است؛ ثالث روی تابلو `off_platform` می‌ماند تا `CY-009`.
- طرف قرارداد کاربر برای ریل: `escrow` → بانک، `principal_ledger` → صندوق. پلتفرم حساب امانی باز نمی‌کند و bureau/CA نیست.
- پلتفرم در صیاد ظهرنویسی نمی‌کند (`CY-002` استعلام است؛ `CY-007` وضعیت را همگام می‌کند).
- نرخ پیشنهادی لایه ۱ الزام‌آور بازار نیست مگر داخل قرارداد نهاد.
- Feature Flag برای ریل/استعلام جدید؛ کلید خاموش رفتار قبلی را نگه می‌دارد.
- راز و PII خام در لاگ و ریپو ممنوع.
- OCR فقط پیشنهاد فرم است؛ منبع حقیقت فیلد تا تأیید کاربر، ورود دستی + اعتبارسنج آگهی است (`CY-020`).

## ۷. افزودن قابلیت یا برش جدید

1. مقدار جدید وضعیت/موج/ریل را اول در [`taxonomy.md`](taxonomy.md) تعریف کنید.
2. از [`_templates/capability.md`](_templates/capability.md) / [`slice.md`](_templates/slice.md) کپی کنید؛ شناسهٔ `CY-NNN` یکتا و غیرقابل استفادهٔ مجدد.
3. پوشه: `capabilities/CY-NNN-kebab-name/`؛ برش در `slices/`.
4. ردیف INDEX + YAML جلو کارت را در **همان تغییر** به‌روز کنید.
5. فهرست vendor را در کارت تکرار نکنید؛ به `vendor-landscape.md` ارجاع بدهید.
6. User Story برش باید Scope و Capability Types داشته باشد تا در start-prompt کامل باشد.

کارت را `ready` نکنید تا حداقل یک برش پذیرش قابل تست داشته باشد.

## ۹. چک‌لیست شروع برش (انسان)

قبل از `@ai-feature-implementation`:

- [ ] INDEX: این برش «برش بعدی» است و قابلیت `blocked` نیست
- [ ] فایل برش و کارت والد خوانده شده؛ ⚠️ مسدودکننده بسته یا صریحاً خارج از این برش است

- [ ] شاخه از `develop` به‌روز است (`feature/cy-…`)
- [ ] User Story برش عیناً در پرامپت است
- [ ] این راهنما در Additional Context آمده
- [ ] اگر استعلام/هویت/پیامک/امضا/OCR چک: `vendor-landscape.md` هم در پرامپت است

- [ ] پذیرش برش با تست یا شواهد مشخص پاس شده

## ۱۰. چک‌لیست Agent (Chat 1)

اگر کاربر برشی از این کاتالوگ را برای Think آورد:

1. این فایل، کارت والد، فایل برش، و در صورت لزوم `vendor-landscape.md` را Read کن.
2. اگر وضعیت `blocked`/`draft` است یا ⚠️ مسدودکننده باز است: کد ننویس؛ دروازه را اعلام کن.
3. پرامپت را با User Story برش هم‌خوان کن؛ خارج از محدودهٔ برش را گسترش نده.
4. spec را به پذیرش برش گره بزن. Port را بدون URL vendor طراحی کن.
5. پس از شروع Build، `status: in-build` و `impl_path` را به انسان یادآوری کن (انسان باید YAML/INDEX را در همان PR ببیند).

Skill Think/Build را بدون نام‌بردن کاربر از `@ai-feature-implementation` برای این کار بزرگ خودسرانه اجرا نکن.

## ۱۱. بعد از `shipped`

- سند پایه را فقط اگر رفتار محصول جاری عوض شده به‌روز کنید.
- برش بعدی همان قابلیت را در INDEX بنویسید؛ قابلیت وقتی همهٔ برش‌های متعهد پایلوت shipped شدند می‌تواند روی کارت `shipped` بماند و برش جدید `draft` جدا بگیرد.
- شاخهٔ feature را طبق نقطهٔ ۳ GitFlow پاک کنید.
- تصمیم vendor را در دفتر [`vendor-landscape.md`](vendor-landscape.md) بنویسید تا برش بعدی همان لایه از صفر شروع نکند.
