# منظرهٔ ارائه‌دهندگان بیرونی

**نقش این فایل:** SSOT انتخاب **لایهٔ برونسپاری** و **کاندیدهای B2B** برای اتصال زنده. جایگزین کارت قابلیت، قرارداد API، یا انتخاب نهایی تجاری نیست.

**به‌روزرسانی پژوهش:** ۱۴۰۵/۰۶/۰۸ (2026-08-30). فهرست vendor کهنه می‌شود؛ قبل از قفل آداپتر باید لینک‌ها را دوباره باز کرد.

**قفل vendor در دامنه ممنوع است.** الگوی اجباری: Port داخلی + آداپتر قابل تعویض + Feature Flag + failover به صف دستی/stub. مرجع معماری: `CY-008` و `doion.integrations`.

---

## ۰. حتماً هنگام پیاده‌سازی (از قلم نیفتد)

این سند را باز کن اگر برش مربوط به یکی از این‌هاست:

| لایه | قابلیت / برش | دامنه |
|------|----------------|--------|
| استعلام هویت حقیقی | `CY-001-b` | `identity` |
| KYB حقوقی | `CY-001-c` | `identity` |
| eKYC بیومتریک | `CY-001-d` | `identity` |
| SMS / OTP | `CY-001-a` | `notifications` / `integrations` |
| وضعیت همین چک صیادی | `CY-002` | `checks` |
| اعتبار صادرکننده | `CY-019` | `compliance` |
| امضای دیجیتال قرارداد | `CY-007-c` | `matching` |
| تطبیق شبا/کارت (جانبی) | همراه KYC یا ریل شریک | `identity` / `integrations` |
| OCR تصویر چک / کمک ورود آگهی | `CY-020` | `checks` |

**کار انسان:** کارت قابلیت + [`usage-guide.md`](usage-guide.md) + این فایل + (در صورت Think/Build) skill `ai-feature-implementation`.  
**کار Agent:** بخش [پرامپت تحقیق هنگام پیاده‌سازی](#پرامپت-تحقیق-هنگام-پیاده‌سازی) را اجرا کند؛ vendor را در مدل دامنه hard-code نکند. فرآیند اجرا: [`usage-guide.md`](usage-guide.md).

قوانین سخت:

1. بازار ایران **چند محصول جدا** است، نه یک vendor واحد. SMS ≠ KYC ≠ bureau ≠ صیاد ≠ امضا ≠ OCR تصویر.
2. پلتفرم صادرکنندهٔ هویت ملی، bureau، CA، یا بانک نیست؛ داده را با رضایت می‌فرستد و نتیجه را به وضعیت داخلی نگاشت می‌کند.
3. قطع تأمین‌کننده یا `PROVIDER_ERROR` / ۵۰۲ هرگز `approved` خاموش نمی‌سازد.
4. درگاه خرد مصرف‌کننده (پرداخت به‌ازای استعلام «فقط خودم») backend پایلوت نیست مگر قرارداد سازمانی + API پایدار + مبنای رضایت روشن باشد.
5. امانی/پرداخت W1 منبع حقیقت‌اش **بانک یا صندوق هم‌برند** است، نه کیف‌پول PSP — مگر شریک صریح همان مسیر را بپذیرد.

## پرامپت تحقیق هنگام پیاده‌سازی

در چت Cursor (ترجیحاً Chat 1 مهارت `ai-feature-implementation`) این بلوک را بده. Agent باید لینک‌های زنده را fetch کند؛ به حافظهٔ این فایل بسنده نکند.

```text
در حال انتخاب ارائه‌دهنده برای برش <CY-NNN-x> هستم. کد آداپتر زنده ننویس تا انتخاب و Port مشخص شود.

الزامی:
1. بخوان: docs/capability-roadmap/vendor-landscape.md
2. بخوان: کارت قابلیت و فایل برش مربوط
3. سه کاندید همان لایه را از روی جدول این سند پیدا کن و صفحهٔ محصول + مستندات API را امروز باز کن (ممکن است کهنه باشد)
4. جدول امتیاز بخش ۳ را برای این سه پر کن (با شواهد لینک، نه حدس)
5. خروجی:
   - توصیهٔ پایلوت (یک primary + یک fallback)
   - قرارداد Port داخلی (ورودی/خروجی/خطا) مستقل از schema یک vendor
   - نگاشت کدهای خطا به approved / rejected / pending+صف دستی
   - فیلدهایی که محصول امروز ندارد (مثلاً تاریخ تولد) و باید قبل از فلگ زنده اضافه شود
   - سؤال‌های ⚠️ باز کارت که هنوز مانع قراردادند
6. ممنوع: قفل URL/SDK یک vendor در دامنهٔ identity/checks/matching؛ secret در ریپو؛ ادعای «رتبهٔ رسمی چک‌یار» یا «انتقال در صیاد توسط پلتفرم»

اگر مستند vendor با این فایل تعارض داشت، مستند زنده را مبنا بگیر و تعارض را صریح بگو.
```

پس از قرارداد تجاری، ردیف را در [دفتر تصمیم پایلوت](#دفتر-تصمیم-پایلوت) پر کن.

## ۱. اصل تفکیک: چه را می‌خریم، چه را نگه می‌داریم

| در پلتفرم می‌ماند | از بیرون خریده می‌شود |
|-------------------|------------------------|
| ویزارد KYC، رضایت، تصمیم `approved`/`rejected`، صف ناظر، audit، فلگ | شاهکار، ثبت احوال، هویت با کدملی |
| آگهی، moderation، بازارچه، Match | اطلاعات شرکت و امضاداران |
| قالب قرارداد، گیت آزادسازی، ماشین‌حالت معامله | جلسهٔ بیومتریک و گواهی امضا |
| نرخ پیشنهادی و سیاست نمایش نمره | وضعیت/رنگ **همین** چک صیادی |
| مدل چندنهادی و دروازهٔ طرف معامله | رتبه/سابقهٔ اعتباری **صادرکننده** |
| UI چک‌یار | OTP پیامک |
| تأیید کاربر روی فیلد آگهی | خواندن نویسه از تصویر چک |

یکپارچه‌سازی برونسپاری کامل نیست: Port + آداپتر + failover.

## ۲. لایه‌ها و سه کاندید معتبر (B2B)

کاندیدها **پیشنهاد پژوهش**اند نه برنده. ترتیب داخل هر جدول اولویت خرید نیست.

### ۲.۱ استعلام هویت حقیقی — `CY-001-b`

چه می‌خریم: تطبیق موبایل↔کدملی (شاهکار)؛ تطبیق نام/کدملی/تاریخ تولد؛ در صورت نیاز استعلام ثبت احوال.

| # | ارائه‌دهنده | مدرک | یادداشت برای چک‌یار |
|---|-------------|------|---------------------|
| ۱ | وندار | [KYC استعلام](https://docs.vandar.io/inquiry_service/inquiry/kyc_not_registered)، [شاهکار](https://docs.vandar.io/inquiry_service/inquiry) | REST؛ درصد تطبیق نام (پیشنهاد خودشان ≥۸۰ — آستانه در config نه magic number دامنه)؛ ۲۰۰ تطبیق و ۴۰۰ عدم‌تطبیق هر دو کارمزدی؛ ۵۰۲ تأمین‌کننده بدون کارمزد |
| ۲ | جیبیت | [استعلام هویتی](https://jibit.ir/identicator/)، [شش ابزار هویت](https://jibit.ir/blog/identity-verification-services/) | شاهکار، ثبت‌احوال مقایسه‌ای، اطلاعات هویتی، اتباع؛ فعال‌سازی از پنل پذیرنده |
| ۳ | یوآیدی | [API شاهکار](https://u-id.net/api-shahkar/) | اگر `CY-001-d` هم از همین vendor باشد، یک قرارداد کمتر |

جایگزین: فینوتک (هاب بانکی+هویتی). در این سند برای تنوع به صیاد/اعتبار تخصیص داده شده.

پیش‌نیاز محصول: مدل `Verification` امروز تاریخ تولد ندارد؛ بدون آن فلگ `kyc_inquiry_live` روشن نشود.

تحقیق مجدد: فیلدهای اجباری، شکل درصد تطبیق در برابر boolean شاهکار، کد خطای کیف‌پول، sandbox.

### ۲.۲ KYB حقوقی — `CY-001-c`

چه می‌خریم: شناسهٔ ملی شرکت → نام/ثبت/نوع/نشانی؛ فهرست امضاداران یا هیئت‌مدیره.

| # | ارائه‌دهنده | مدرک | یادداشت |
|---|-------------|------|---------|
| ۱ | وندار | [مطلب KYB](https://vandar.io/blog/%d8%a7%d8%ad%d8%b1%d8%a7%d8%b2-%d9%87%d9%88%db%8c%d8%aa-%d8%a7%d8%b4%d8%ae%d8%a7%d8%b5-%d8%ad%d9%82%d9%88%d9%82%db%8c-kyb/) | دو API جدا: شرکت و صاحبین امضا |
| ۲ | جیبیت | [سرویس KYB](https://jibit.ir/blog/jibit-kyb-service/) | پوشش وسیع‌تر: مدیرعامل، روزنامه رسمی، مجوز، شرکت مادر/زیرمجموعه — برای پایلوت همه لازم نیست |
| ۳ | فینوتک | [رونمایی KYB حقوقی](https://peivast.com/p/215620) | اعضا + آگهی؛ اعتبارسنجی حقوقی با OTP به مدیرعامل (آن بخش → نزدیک `CY-019` حقوقی) |

پیشنهاد پایلوت محصول: استعلام ضمیمهٔ صف ناظر؛ `approved` خودکار حقوقی معمولاً زود است.

مسیر حقوقی API حقیقیِ نام/تولد را صدا نزند.

### ۲.۳ eKYC بیومتریک — `CY-001-d`

فقط اگر نهاد هم‌برند مشتری‌پذیری ویدئویی بخواهد. وگرنه برش `blocked` می‌ماند.

| # | ارائه‌دهنده | مدرک | یادداشت |
|---|-------------|------|---------|
| ۱ | فراشناسا | [احراز غیرحضوری](https://farashenasa.ir/%d8%ae%d8%af%d9%85%d8%a7%d8%aa-%d8%a7%d8%ad%d8%b1%d8%a7%d8%b2-%d9%87%d9%88%db%8c%d8%aa-%d8%ba%db%8c%d8%b1-%d8%ad%d8%b6%d9%88%d8%b1%db%8c-%d8%a8%db%8c%d9%88%d9%85%d8%aa%d8%b1%db%8c%da%a9/) | SDK / API / Webview؛ verification + liveness + awareness؛ مقایسه با عکس ثبت احوال |
| ۲ | یوآیدی | [مستندات API eKYC](https://u-id.net/api-ekyc-docs/) | PWA/API؛ سلفی + سریال کارت ملی؛ callback |
| ۳ | جیبیت | [SDK در برابر API در برابر Gateway](https://jibit.ir/blog/jibits-kyc-onboarding-frames/) | اگر استعلام هم جیبیت باشد، یک قرارداد |

پلتفرم انبار بیومتریک ملی نیست. نتیجه فقط از callback/استعلام وضعیت با همبستگی `verification_id`. فایل چهره در لاگ یا قرارداد API عمومی چک‌یار برنگردد.

مقالهٔ مفهومی [KYC چیست — فراشناسا](https://farashenasa.ir/%D9%85%D8%B9%D9%86%DB%8C-%D9%88-%D9%85%D9%81%D9%87%D9%88%D9%85-kyc-%D9%88-%D8%A7%D9%87%D9%85%DB%8C%D8%AA-%D8%A2%D9%86-%D8%AF%D8%B1-%D8%AF%D9%86%DB%8C%D8%A7%DB%8C-%D8%AA%D8%AC%D8%A7%D8%B1%D8%AA/) سرویس اجرایی نیست؛ فقط KYC ≠ AML.

### ۲.۴ SMS / OTP — `CY-001-a`

هیچ‌کدام از vendorهای هویت بالا پیامک نیستند. در کد از قبل `kavenegar` و `melipayamak` در `SMSProvider` رزرو شده‌اند.

| # | ارائه‌دهنده | مدرک | یادداشت |
|---|-------------|------|---------|
| ۱ | کاوه‌نگار | [kavenegar.com](https://kavenegar.com/)، [OTP](https://kavenegar.com/sms/verification) | Lookup الگو؛ خط خدماتی؛ failover تماس صوتی |
| ۲ | ملی‌پیامک | REST + Auth Token | همان نام در constants |
| ۳ | مگفا | [سیستم پیام‌دهی](https://magfa.com/messaging-systems/) | سازمانی؛ پیش‌شماره ۳۰۰۰؛ SMPP/HTTP |

OTP ورود نیازمند **خط خدماتی** است. متن پیام در لاگ production نیاید. Secret فقط env.

### ۲.۵ وضعیت همین چک صیادی — `CY-002`

وضعیت/ثبت/رنگ **همین برگه**، نه سابقهٔ شخص (`CY-019`) و نه ظهرنویسی (`CY-007`).

| # | ارائه‌دهنده | مدرک | یادداشت |
|---|-------------|------|---------|
| ۱ | فینوتک | [اعتبارسنجی / صیاد](https://finnotech.ir/service/%D8%B3%D8%B1%D9%88%DB%8C%D8%B3-%D9%87%D8%A7%DB%8C-%D8%A7%D8%B9%D8%AA%D8%A8%D8%A7%D8%B1%D8%B3%D9%86%D8%AC%DB%8C) | رنگ چک، شناسه صیادی، زنجیره — نزدیک نیاز آگهی |
| ۲ | جیبیت | [استعلام چک صیادی](https://jibit.ir/blog/cheque-inquiry-service-sayad-system/) | B2B با شناسه ۱۶ رقمی + حقیقی/حقوقی دارنده |
| ۳ | فرابوم | [faraboom.ir](https://faraboom.ir/) | هاب بانکداری باز؛ اگر شریک بانکی روی بوم باشد مسیر کوتاه‌تر |

جایگزین اغلب بهتر: کانال مستقیم **بانک هم‌برند**. اگر API قانونی نباشد کارت `blocked` می‌ماند. پلتفرم endpoint ظهرنویسی ندارد.

### ۲.۶ اعتبار صادرکننده — `CY-019`

KYC می‌گوید آگهی‌دهنده کیست. کیفیت آگهی و سقف خرید صندوق به **صادرکنندهٔ روی چک** بستگی دارد.

| # | ارائه‌دهنده | مدرک | یادداشت |
|---|-------------|------|---------|
| ۱ | فینوتک | همان بستهٔ اعتبارسنجی؛ [راه پرداخت](https://way2pay.ir/487316/) | برگشتی، تسهیلات، زنجیره، چک در راه؛ با مجوز کاربر |
| ۲ | یوآیدی | [اعتبار معاملاتی](https://u-id.net/justice-profile-docs/) | OTP رضایت روی موبایل سوژه — برای صادرکنندهٔ ثالث ممکن است گیر حقوقی بدهد |
| ۳ | شرکت اعتبارسنجی ایران (ICS) | [ics24.ir](https://ics24.ir/)، [mycredit.ir](https://www.mycredit.ir/) — سرویس «اعتبار من» سازمانی | منبع رسمی رتبه A1–E3 / ۰–۹۰۰؛ عضویت نهادی نه اسکرپ |

**نگذار به‌عنوان backend پایلوت:** [پیشخوانک اعتبار معاملاتی](https://pishkhanak.com/services/transaction-check) و [کد مکنا](https://pishkhanak.com/services/inquiry-makna-code) مگر API سازمانی جدا و مبنای رضایت برای استعلام شخص ثالث روشن باشد. معمولاً استعلام «فقط خودم» است.

پلتفرم bureau نیست. در W1 نمره به سرمایه‌گذار ثالث نشان داده نشود مگر شریک صریح بگوید. UI «رتبهٔ رسمی چک‌یار» یا «سود تضمینی» ندارد.

سؤال باز مسدودکننده: آیا دارنده می‌تواند برای استعلام اعتبار **صادرکننده** رضایت بدهد؟

### ۲.۷ امضای دیجیتال واجد شرایط — `CY-007-c`

اگر شریک کلیک‌رپ را کافی نداند. پلتفرم CA نیست. قرارداد به‌نام نهاد هم‌برند.

| # | ارائه‌دهنده | مدرک | یادداشت |
|---|-------------|------|---------|
| ۱ | فراشناسا | [امضای دیجیتال](https://farashenasa.ir/%d8%b3%d8%b1%d9%88%db%8c%d8%b3-%d8%a7%d9%85%d8%b6%d8%a7%db%8c-%d8%af%db%8c%d8%ac%db%8c%d8%aa%d8%a7%d9%84/) | موبایل‌محور، بدون توکن؛ RA به چند CA؛ معمولاً بعد از KYC بیومتریک همان گروه |
| ۲ | امضامی | [emza.me](https://emza.me/) | اپ + پنل/API ارسال سند به امضاکنندگان |
| ۳ | آسان‌امضا (پندار کوشک ایمن) | [API softsign](https://pki.co.ir/download/SS/PKI-SS-API-DG.pdf) | امضای ابری سازمانی؛ اتصال به چند مرکز میانی |

ریشهٔ قانونی: [مرکز میانی عام / GICA](https://gica.ir/portal/) — مرجع صدور است نه محصول یکپارچه‌سازی چک‌یار. اعتبار ادعا به گواهی ارائه‌دهنده و قانون تجارت الکترونیک ۱۳۸۲ است نه برند چک‌یار.

### ۲.۸ تطبیق شبا / کارت با کدملی (جانبی)

برای لایهٔ ۱ حیاتی نیست؛ هنگام تسویه یا امانی مفید است.

| # | ارائه‌دهنده | پوشش نمونه |
|---|-------------|------------|
| ۱ | وندار | تطبیق شبا↔کدملی، کارت↔موبایل، تبدیل کارت به شبا |
| ۲ | جیبیت | تطبیق کارت/حساب/شبا با کدملی و با نام |
| ۳ | فرابوم | همان خانواده روی هاب باز |

### ۲.۹ OCR تصویر چک (کمک ورود، نه حقیقت وضعیت) — `CY-020`

چه می‌خریم: استخراج ساخت‌یافته از عکس چک صیادی (شناسه ۱۶ رقمی و در صورت پوشش مبلغ/تاریخ/بانک) تا فرم آگهی **پیشنهاد** شود. ورود دستی می‌ماند. OCR جایگزین استعلام صیاد (`CY-002`) یا bureau (`CY-019`) نیست.

| # | ارائه‌دهنده | مدرک | یادداشت برای چک‌یار |
|---|-------------|------|---------------------|
| ۱ | جیبیت | [OCR چک صیادی](https://jibit.ir/blog/jibits-sayadi-cheque-ocr/)، [اسکن چک در KYC Gateway](https://kycgateway.jibit.ir/kyc/docs) | ابری و on-prem؛ خروجی شماره + `accuracy`؛ مناسب اگر تصویر نباید از شبکهٔ نهاد خارج شود |
| ۲ | ونیفای | [venify.ir](https://venify.ir/)، [گزارش راه پرداخت](https://way2pay.ir/474516/) | چاپ (صیاد، شبا) و دست‌نویس (مبلغ، تاریخ)؛ اغلب با استعلام پیچک **بسته** می‌فروشند — در Port این لایه فقط استخراج را بگیرید |
| ۳ | پادیوم | [قیمت: پردازش تصویر OCR چک](https://blog.podium.ir/podium-price-update-1404/)، [بازارچه/مستند](https://podium.sandpod.ir/docs) | سرویس جدا «دریافت اطلاعات چک از روی تصویر» (شناسه ۳۸۸۱۰۵۶)؛ تأمین‌کننده ممکن است داتین/عصر داده باشد — قرارداد B2B نه اسکرپ |

**نگذار به‌عنوان backend پایلوت:** صفحات دایرکتوری مثل [api.ir](https://www.api.ir/) بدون قرارداد سازمانی و SLA. بستهٔ «یک API هم OCR هم وضعیت صیاد» را در دامنه یکی نکنید.

تحقیق مجدد: فیلدهای واقعی JSON، confidence per-field، سقف حجم تصویر، محل پردازش (ابر/on-prem)، آیا دست‌نویس مبلغ را می‌دهند.

### ۲.۱۰ آنچه از این فهرست خریده نمی‌شود

| نیاز | مسیر درست | اشتباه رایج |
|------|-----------|-------------|
| امانی (`CY-005`) | بانک هم‌برند + `SettlementPort` | کیف‌پول وندار/جیبیت به‌جای حساب امانی بانک |
| نقدینگی (`CY-006`) | دفتر/API صندوق | PSP به‌عنوان principal |
| ضمانت وصول (`CY-012`) | نهاد دارای مجوز بیمه/تضمین | ادعای تضمین چک‌یار |
| بازارچه، Match، نرخ، هم‌برند | کد خودمان | سپردن هسته به vendor هویت |
| وضعیت قانونی همین چک | `CY-002` استعلام | قبول خروجی OCR به‌عنوان ثبت/رنگ صیاد |

## ۳. معیار انتخاب (امتیازدهی پایلوت)

هر لایه را جدا امتیاز بده. جمع وزن = ۱۰۰. برندهٔ یک لایه برندهٔ لایه‌های دیگر نیست.

| معیار | وزن پیشنهادی | چه چیزی نمره می‌گیرد |
|--------|---------------|------------------------|
| پوشش فیلدهای Port (نه فیلد اضافهٔ بازاری) | ۲۵ | ورودی/خروجی برش؛ کد خطا قابل نگاشت |
| قرارداد B2B + sandbox + SLA قطعی | ۲۰ | کلید سازمانی، محیط تست، رفتار ۵۰۲/timeout مستند |
| مجوز و رضایت | ۱۵ | آیا استعلام شخص ثالث (صادرکننده) قانونی است؟ OTP سوژه؟ |
| عدم قفل (مستند عمومی، جایگزینی آداپتر) | ۱۰ | بدون SDK اجباری در دامنه؛ REST کافی برای W0 استعلام |
| پایداری و چندتأمین‌کننده | ۱۰ | وندار صریحاً سوئیچ تأمین‌کننده دارد؛ برای صیاد کانال بانک امتیاز جدا |
| هزینهٔ قابل پیش‌بینی | ۱۰ | کارمزد تطبیق ناموفق؛ کیف پول خالی چه می‌کند |
| هم‌مسیر با لایهٔ بعدی همان موج | ۱۰ | مثلاً هویت+KYB از یک واسط؛ SMS جدا ماندن امتیاز منفی ندارد |

حد نصاب پیشنهادی پایلوت: هیچ معیار «مجوز و رضایت» زیر قبولی نباشد — حتی اگر جمع کل بالا باشد.

خروجی امتیاز را در `ai-documents/features/<kebab>/` کنار spec همان برش ذخیره کن (مثلاً `vendor-score.md`) تا با کد آداپتر هم‌خوان بماند.

## ۴. قرارداد Port — حداقل فیلد (قبل از آداپتر زنده)

دامنه این شکل‌ها را می‌فهمد؛ آداپتر vendor را ترجمه می‌کند.

### هویت حقیقی

- ورودی: `national_id`, `mobile`, `first_name`/`last_name` یا `full_name`, `birth_date` (جلالی، فرمت در آداپتر)
- خروجی: `shahkar_matched` (bool | unknown)، `name_similarity_percent` (اختیاری)، `inquiry_track_id`
- خطا: `unmatched` | `provider_error` | `insufficient_credit` | `timeout`

### KYB

- ورودی: `company_national_id` (۱۱ رقم، از قبل validate)
- خروجی: نام، نوع، تاریخ/شماره ثبت، نشانی خلاصه؛ فهرست امضاداران حداقل `name` + `position` در صورت وجود
- خطا: `not_found` | `provider_error` | …

### SMS

- همان اینترفیس فعلی `send_sms(phone, message, provider)` + وضعیت `SMSLog`
- فلگ خاموش = stub فعلی

### صیاد (همین چک)

- ورودی: شناسهٔ صیادی + در صورت الزام تأمین‌کننده هویت دارنده
- خروجی: وضعیت مجاز برای moderation (enum داخلی، نه رشتهٔ خام vendor در API عمومی)
- نمایش به ثالث W1: فقط فیلدهایی که شریک اجازه داده

### اعتبار صادرکننده

- ورودی: شناسهٔ سوژه طبق تصمیم حقوقی (کدملی صادرکننده و/یا دارنده) + رضایت ثبت‌شده
- خروجی: خلاصهٔ داخلی برای ناظر/صندوق؛ **بدون** فیلد نمره در API عمومی آگهی مگر فلگ جدا
- خطا: قطع bureau → صف با برچسب استعلام ناموفق؛ انتشار با نمرهٔ کهنه ممنوع

### OCR چک (پیشنهاد فرم)

- ورودی: `document_id` نوع `cheque_image` یا بایت تصویر با سقف حجم در config
- خروجی: پیشنهادهای اختیاری `cheque_serial_number`, `face_amount`, `due_date`, شناسهٔ بانک کاتالوگ در صورت تشخیص؛ `confidence` per-field
- خطا: `unreadable` | `provider_error` | `timeout` | `unsupported_type`
- زیر آستانه: فیلد را خالی برگردان یا `needs_review` — هرگز آگهی را منتشر نکن
- ممنوع در این Port: وضعیت صیاد، نمرهٔ bureau، `approved` آگهی

### بیومتریک / امضا

- همبستگی با `verification_id` یا `contract_id` + `template_version` قفل‌شده
- وضعیت: `pending` | `succeeded` | `failed` | `expired`
- بدون بازگرداندن باینری چهره/کلید خصوصی در API چک‌یار

## ۵. نگاشت شرکت → چند لایه

یک شرکت می‌تواند چند لایه بفروشد؛ Port جدا بماند.

| شرکت | لایه‌های مرتبط در این سند |
|------|---------------------------|
| وندار | هویت، KYB، شبا/کارت — نه SMS؛ PSP به‌جای امانی بانک نه |
| جیبیت | هویت، KYB، بیومتریک، صیاد، شبا/کارت، OCR چک |
| ونیفای | OCR چک (+ بستهٔ استعلام جدا؛ قاطی با `CY-002` ممنوع) |
| پادیوم | OCR تصویر چک (بازارچه؛ تأمین‌کننده ممکن است جدا باشد) |
| یوآیدی | هویت، بیومتریک، اعتبار معاملاتی (`CY-019` نه KYC کاربر) |
| فینوتک | KYB، صیاد، اعتبار — جایگزین کامل KYC کاربر نیست |
| فراشناسا | بیومتریک، امضا — شاهکار/SMS نیست |
| کاوه‌نگار / ملی‌پیامک / مگفا | فقط SMS |
| فرابوم | صیاد (در حد هاب)، شبا/کارت؛ هویت کامل KYC نیست |
| ICS / mycredit | منبع رتبه؛ معمولاً از کانال نهادی |
